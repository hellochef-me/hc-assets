## Writer authority and uncertain outcomes

The default local authority is `DirectSheetWriter` in this workspace on this Mac, using existing approved Google JWT/REST credentials. A filesystem lock coordinates local processes; the asynchronous native command core retains the reviewed durable-intent/atomic-batch protocol. It needs no gateway deployment or signing secret. Another host/workspace/script/collaborator is outside this lock. The optional gateway authority is one Apps Script project; every Next server instance would send commands to that project. [ScriptLock is scoped to its script](https://developers.google.com/apps-script/reference/lock/lock-service), and [Sheet batchUpdate applies a batch together but does not prevent collaborator edits](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate). A Next local mutex is not used for this integration. No Sheet-native unique constraint or compare-and-swap is claimed.

While holding its lock, either controlled writer reads fresh Inventory/Employees/metadata, validates revision and serial, and creates a durable **pending intent** before submitting asset changes. The domain batch writes Inventory, legacy event, complete movement, revision/photo metadata and committed command receipt together, using stringValue cells so user text is never interpreted as a formula. Old history is appended to and never rewritten. Original unmapped legacy values are retained when corresponding domain fields did not change; CPU/RAM/disk/model-year are not guessed from general specs.

Retry with the same request UUID and unchanged payload reads an already committed receipt, including after an acknowledgement was lost. A different payload under that UUID is rejected. If a script terminates or the upstream outcome remains uncertain, its pending intent blocks **all** later commands, even different UUIDs/serials. This avoids a late first batch racing a second submission after lock release. Availability is intentionally sacrificed: an authorized operator must reconcile after confirming no requests remain in flight. There is no automatic stale-lock/intent expiry, resend, receipt deletion or repair endpoint.

This depends on exclusive write ownership: Anthony confirmed the old site is unused and this local app is the only writer. Another script project or Sheet collaborator can bypass this lock and race a read/check/write; fingerprints detect previous external edits but cannot fence concurrent ones. If editable Sheets must remain collaborative, select a transactional database as authority and treat Sheets as a projection. That database/outbox alternative is not implemented.

Approved, provisioned hidden sidecars: HCAssets_records (`id,version,part,json`), HCAssets_movements (`id,json`), HCAssets_commands (`requestId,digest,part,json`). Photos/full records and immutable receipts use 44,000-character chunks under cell limits; originals remain local in the preview. Base Inventory/assignment_history headers must match exactly for the writer; aliases are not silently migrated. A one-time setup batch added only these tabs/headers and verified original row hashes unchanged. Record/receipt growth and Sheet quotas must be capacity-tested; a private object-storage photo strategy can replace inline chunks after a retention/access decision. This is not an unlimited-scale photo store.
