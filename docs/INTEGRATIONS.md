# Integrations — implementation and activation status

The current preview uses a timestamped, authorized read-only import of the real Sheet (51 assets, 7 history events, 67 employee rows), preserving IDs and legacy values. It denies writes and paid AI. Explicit fictional demo mode uses a separate local store. Live-readonly and isolated staging selectors, route/UI wiring, OCR, cited resale and controlled Sheet persistence are implemented; no runtime credentials, gateway deployment or paid network tests are configured. No Google rows/headers/tabs were changed. See the exact [secure handoff](SECURE-HANDOFF.md).

Dynamic rendering, anti-bot/login, omitted used condition, nonmatching specs, unavailable source or unsupported currency produces no comparable. No conversion, invented price or model estimate is used. These are asking prices, not completed-sale evidence. Exact contiguous spec matching can exclude otherwise plausible comparisons. Titles and conditions are copied evidence; no battery/function claim is inferred. Source checkedAt is server-generated. No serial, employee, purchase cost or photo enters a market search. Current page access and live model/tool support remain untested.

## Writer authority and uncertain outcomes

The proposed authority is one Apps Script project; every authenticated Next server instance sends commands to that project. [ScriptLock is scoped to its script](https://developers.google.com/apps-script/reference/lock/lock-service), and [Sheet batchUpdate applies a batch together but does not prevent collaborator edits](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate). A Next local mutex is not used for this integration. No Sheet-native unique constraint or compare-and-swap is claimed.

While holding the lock, the gateway reads fresh Inventory/Employees/metadata, validates revision and serial, and creates a durable **pending intent** before submitting asset changes. The domain batch writes Inventory, legacy event, complete movement, revision/photo metadata and committed command receipt together, using stringValue cells so user text is never interpreted as a formula. Old history is appended to and never rewritten. Original unmapped legacy values are retained when corresponding domain fields did not change; CPU/RAM/disk/model-year are not guessed from general specs.

Retry with the same request UUID and unchanged payload reads an already committed receipt, including after an acknowledgement was lost. A different payload under that UUID is rejected. If a script terminates or the upstream outcome remains uncertain, its pending intent blocks **all** later commands, even different UUIDs/serials. This avoids a late first batch racing a second submission after lock release. Availability is intentionally sacrificed: an authorized operator must reconcile after confirming no requests remain in flight. There is no automatic stale-lock/intent expiry, resend, receipt deletion or repair endpoint.

This depends on exclusive write ownership: disable the old gateway and disallow manual/API writes before activation. Another script project or Sheet collaborator can bypass this lock and race a read/check/write; fingerprints detect previous external edits but cannot fence concurrent ones. If editable Sheets must remain collaborative, select a transactional database as authority and treat Sheets as a projection. That database/outbox alternative is not implemented.

Proposed reviewed sidecars (not created): HCAssets_records (`id,version,part,json`), HCAssets_movements (`id,json`), HCAssets_commands (`requestId,digest,part,json`). Photos/full records and immutable receipts use 44,000-character chunks under cell limits; originals remain local in the preview. Base Inventory/assignment_history headers must match exactly for the writer; aliases are not silently migrated. No schema provisioning script executes. Record/receipt growth and Sheet quotas must be capacity-tested; a private object-storage photo strategy can replace inline chunks after a retention/access decision. This is not an unlimited-scale photo store.

## Remaining work, separated by cause

**Configuration/permission/approval, intentionally untouched:** secure reuse of the approved existing BC OpenAI key; explicit tested vision/search model selection; approved Google read identity/access; spreadsheet ID; an approved singleton gateway deployment and signing-secret delivery; Advanced Sheets enablement and [quota review](https://developers.google.com/apps-script/guides/services/quotas); backup/schema/sidecar approval; exclusive writer cutover; hosting selection. The suggested signing interface is source only, not a provisioned new key. None of these has been configured. The existing connected-tool read used for the import does not provide credentials to the Next server.

**Missing application code, deliberately deferred with auth:** authentication/session/authorization and trusted actor resolution; distributed and monetary spend controls; production logging/monitoring and an authorized pending-command reconciliation/admin workflow. Runtime adapter selection, route/UI wiring and local persistent request limits are implemented and tested with mocked providers. Staging explicitly rejects the production Sheet ID. AI needs the staging mode, approval flag, key and both model IDs; current configuration disables it. No public exposure is allowed while auth is deferred.

**Acceptance/operational validation:** read-only schema/count/ID reconciliation completed for the snapshot; ongoing live reads and staging-copy end-to-end Google/Apps Script writes, real ScriptLock contention and interrupted execution; real model vision/web-search/network/source access; physical camera/HEIC/mobile Safari/keyboard and accessibility acceptance; snapshot/receipt capacity and private photo retention; backup/rollback/reconciliation drills. Network contracts are mocked, so provider availability, cost and correctness are not certified. No production deployment or PR publication is approved.
